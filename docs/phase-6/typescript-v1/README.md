# TypeScript context-quality baseline v1 (`contextbench-ts-v1`)

The first evaluation of OXIDE's TypeScript context on real repositories and tasks
([docs/typescript.md](../../typescript.md) is the slice it measures). It reuses the
ContextBench-py ruler unchanged — the metrics, loss stages, audit rules and gate rules
of [`baseline-v2`](../baseline-v2/README.md), by calling `tests/python/contextbench.py`
— and adds only what TypeScript needs: a TypeScript corpus, module-level lines from
the grammar, and a structural cause for every span lost before packing. The Python
baselines (`baseline-v1` … `baseline-v4`) and their gate are untouched.

Claims: entry-point retrieval, TreeRouter coverage and packed-context quality of the
deterministic offline engine on 89 TypeScript tasks with independently defined gold,
and where the evidence is lost. It makes no downstream-agent claim. It is a baseline
for future TypeScript work, not a quality target.

## Protocol (written before any quality result was produced)

Fixed before the harness first scored a ContextBench task. The one engine fact known
before this was written is that the largest vscode corpus does not index with the
product's LadybugDB buffer pool (see § Buffer pool), an operational result, not a
quality one. Changing anything here later needs a new baseline version.

### Tasks and gold

- **fixture** (8 tasks, dev): every `repo: ts` query of `fixtures/benchmark.json` and
  `fixtures/structural_benchmark.json`, corpus `fixtures/ts_repo`, as ContextBench-py
  does for Python. Gold symbols (`file#A.b`) map to line spans with the
  `tree-sitter-typescript` grammar directly (the declaration statement, `export`
  included), never with OXIDE's derivation or results; `file#file:__module__` is the
  whole file.
- **ContextBench** (81 tasks): `EuniAI/ContextBench` `data/full.parquet` (sha256
  `2f56535b…ee61ca8`, the file ContextBench-py uses). Of its 119 `language ==
  typescript` tasks, every task whose repository (by URL: ContextBench names mui both
  `mui/material` and `mui/material-ui`) meets the cost rule and that has at least one
  gold span in a TypeScript source:

  | Repository | `typescript` tasks | Eligible | TS files at base commits |
  | --- | ---: | ---: | --- |
  | mui/material-ui | 84 | 48 | 272–3,941 |
  | vuejs/core | 15 | 15 | 455–485 |
  | microsoft/vscode | 14 | 14 | 2,944–4,414 |
  | coder/code-server | 2 | 2 | 72–83 |
  | darkreader/darkreader | 2 | 2 | 201–210 |
  | angular/angular | 1 | 0 | 5,289 (over the cost rule) |
  | tailwindlabs/tailwindcss | 1 | 0 | gold only in `.js` and `.lock` files |

  36 mui tasks have gold only in JavaScript, JSON or Markdown and are not tasks here.
  The query is the `problem_statement`, verbatim, without hints. Gold is the
  human-annotated `gold_context` (1-based, inclusive), each span with the sha256 of its
  whitespace-normalized content.
- **Cost rule**: at most 5,000 TypeScript files (`*.ts`, `*.tsx`, `*.mts`, `*.cts`,
  declaration files included) at every base commit of the repository, measured from
  git trees without running OXIDE, and checked again on every fetch.
- **Corpus**: the tracked TypeScript files at `base_commit` (`git archive`), indexed
  whole. JavaScript, JSON, Markdown and every other file are left out, a declared
  difference from a full checkout: OXIDE does not parse them, but they would be file
  entities that compete in lexical retrieval. The `name` of every tracked
  `package.json` is recorded beside the corpus (`<corpus>.packages.json`) for the
  attribution oracle only; OXIDE never reads it.
- **Splits, by repository**, with ContextBench-py's rule: **heldout** = the two
  eligible repositories with the most tasks, mui/material-ui (48) and vuejs/core (15),
  63 tasks; **dev** = fixture, vscode, code-server, darkreader, 26 tasks. TypeScript
  retrieval, resolution, routing or packing work is developed and inspected on dev.
  Held-out per-task results are recorded for the gate but are not used to choose or
  tune a change; read them only to evaluate a finished one. This baseline reads
  held-out results in aggregate and by cause only.

### Gold audit

Every annotated span is checked once against its own content at the pinned corpus,
with ContextBench-py's rules and classes (`exact`, `contained`, `path` verified;
`range`, `revision`, `drift`, `empty`, `unresolved` not), recorded in
[`gold-audit.json`](gold-audit.json) (`contextbench-ts-gold-audit-v1`, generated by
`contextbench_ts.py audit PARQUET`). One class is new: **`outside`**, a span in a file
that is not a TypeScript source. Outside spans are never scored: each task lists them,
and every aggregate reports them by extension, so the gold OXIDE cannot see is a
separate, visible number, not a loss of any stage.

### Metrics

Identical to ContextBench-py scorer v2, computed by its code (`contextbench.score`):
`entry_recall@1/5/20`, `entry_mrr`, `entry_file_recall`, `routed_coverage`, and at
256, 1,024 and 4,096 `oxide-units-v1` `span_recall`, `line_recall`, `file_recall`,
`utilization` and `gold_unit_share`; the stage that lost each incomplete span
(`entry`, `routing`, `unsupported`, `selection`, `budget`); bundle invariants and
output digests. Macro means over the tasks of a split, verified and unverified gold
separately, plus a per-repository breakdown of the gated metrics.

**Module-level lines** (where a file entity covers gold) are lines outside every
outermost declaration by OXIDE's documented symbol rules, computed from the grammar by
`contextbench_ts.declarations`, independently of `oxide.core.typescript`.

**Structural cause** (`cause`) of every span lost at `entry` or `routing` at 4,096
units, first matching rule:

1. `partial-file`: its file parsed partially;
2. `router-bound`: its unit (file, or innermost symbol) is within the router's depth
   (2) of an entry point over the router's edges when no regions, fanout or edge
   bound applies;
3. `unresolved-import`: within that depth only when the oracle's edges are added;
4. `no-path`: neither; retrieval found nothing structurally near it.

The **oracle** is a diagnostic counterfactual, never gold: for each unresolved import,
the file a path rule OXIDE does not apply would pick — a relative module whose name
could not be followed (`relative`), a workspace package by `package.json` name and its
`src/index` or subpath (`workspace`), or the one module whose path ends in a bare
specifier, as `baseUrl` would resolve it (`alias`) — added as a file–file edge.
Corpus counts of import relations (resolved, ambiguous, unresolved by oracle class)
are reported with every corpus.

### Buffer pool

Each corpus is indexed with the product's settings. If LadybugDB's buffer pool
overflows (`Buffer manager exception`), the failure is recorded as the corpus's
`default_index_failure` and the corpus is indexed again with a 512 MiB pool (the
default is 128 MiB). Pool size changes no query result, so quality stays measurable;
the failure is a separate finding.

### Gate rules (`tests/python/test_contextbench_ts.py`)

ContextBench-py's rules: per split, every gated metric at or above its frozen value
minus 0.02; verified task and span counts unchanged; every bundle within budget and
deterministic; corpus identities equal the manifest; output digests equal unless an
engine version changed (reported as a versioned change, never as a quality result);
unverified and outside gold reported in every run. The scorer cases and the task
protocol run in `mise run verify`. The gate itself needs ~3 GB of corpora and tens of
minutes, so it runs as `mise run contextbench-ts`, not in `verify`.

Wall times and memory are written to `performance.json`, never compared: they are not
reproducible.

## Scorer validation

Done before any quality number was read; each item found and fixed a defect, or
confirmed the ruler.

- **Module-level lines agree with OXIDE's views.** For every TypeScript file, the code
  lines outside the grammar's outermost declarations equal the code lines outside the
  symbols OXIDE makes children of the file: 0 of 7,353 files differ (the two fixtures,
  `colinhacks/zod@680d19f7`, `excalidraw/excalidraw@4c37956b`, and the vscode
  `8ce35fa2`, code-server `5d3c9edc`, darkreader `991883df` and one mui corpus;
  measured). The first comparison disagreed on 55 of 528 zod files and found a
  **slice defect**: OXIDE makes object-literal methods and type-literal method
  signatures symbols (`(method_definition) @def` matches everywhere), while
  docs/typescript.md said they are not modeled. The scorer follows the engine's actual
  behavior, since module lines must be what a file view can carry; the doc now records
  the difference. The engine was not changed. The other differences were scorer
  errors (string-named and computed members, destructured exports, non-function
  fields), fixed before any task was scored.
- **Fixture gold** recomputed from the grammar equals the spans of the legacy
  benchmark (`test_tasks_and_audit_are_the_frozen_protocol`), and the harness gives
  the known fixture result: all 8 tasks pack every gold span at 1,024 units, as
  docs/typescript.md measured with a separate script.
- **Two annotation defects in the TypeScript gold**, found by the audit and fixed with
  explicit rules:
  1. 244 spans use absolute container paths (`/workspace/mui__material-ui__0.1/…`),
     the defect `docs/contextbench-scorer-fix` describes. The existing `path` rule
     corrects them when exactly one path suffix holds the content (102 spans).
  2. 127 spans hold their content in `cat -n` form (`12\tcode`). `unnumbered` strips
     the numbers only when every line carries one and they count up from the span's
     first line (an empty last line may have lost its tab); such spans are flagged
     `numbered`. Before this rule, 141 spans were `unresolved`; after it, 39 are,
     26 of them agent-written scratch files (`reproduce.tsx`, `scripts/temp_repro/…`)
     that were never in the repository.
- **Attribution** has regression cases for each cause (a workspace import, an
  unrelated file, a broken file) and was checked by hand on dev. For example, in
  vscode-149380 the entry point `runInExternalTerminal` is in a file that imports
  `prepareCommand` from `'vs/workbench/contrib/debug/node/terminals'`, a `baseUrl`
  path that OXIDE leaves unresolved; the gold span is in that file. A harness bug found
  while writing the results (per-corpus resolution counts overwrote the relation count
  in the manifest) was fixed before the freeze; it changed no result.
- **Reproducibility.** Two independent runs gave byte-identical `results.json`,
  `metrics.json` and `manifest.json`, and a third run with the final scorer gave the
  same `results.json`. The derivation id is baseline-v4's: the engine is the one
  measured for Python.

### Representative failures (dev)

- **Retrieval misses the file entirely** (vscode-106767, -148971, -153857, -160342):
  long issue reports describe UI behavior ("completions which use spaces are broken"),
  none of the 20 entry points is in a gold file, and none is within two hops of one
  (`no-path`).
- **Unresolved `baseUrl` import** (vscode-149380, -164396, -153121, -109750): an entry
  point's file imports the gold file by `vs/…` path; with that edge the gold is one or
  two hops away.
- **Reached but not packed** (code-server-4923): the route stops at 64 regions with
  160 deferred; of the routed gold, `cli.ts` 175–180 is below the value floor and
  `app.ts` 130–134 is omitted for budget; three spans are cut by the router's bound.
- **Fixture**: everything is complete at 1,024 units; the fixture is a regression
  floor, not evidence of real-repository quality.

### Limitations of the benchmark

- 81 real tasks from 5 repositories, two of them with 2 tasks each; held-out is two
  repositories, 77% of it mui. Repository effects dominate, so no confidence intervals
  are claimed; per-repository numbers are reported instead.
- Corpora are TypeScript only. In a real checkout JavaScript, JSON and Markdown files
  compete as file entities; 398 annotated spans are in such files and are not scored.
- ContextBench gold is the context the annotated agent used, not a minimal set; 61
  spans are unverified (range errors, drift, scratch files), and `gold_unit_share` is a
  lower bound on useful context.
- The oracle is a heuristic: `alias` requires a unique path suffix, `workspace`
  ignores `package.json` `exports` and `main`, and neither reads `tsconfig.json`. Its
  counts are an upper bound on what resolution alone could add to routing, since a new
  edge still competes for the router's 64 regions.
- No downstream-agent result; no comparison of OXIDE against a plain grep baseline.

### Evidence-based priorities

In order of measured impact on lost spans:

1. **Entry-point retrieval on long TypeScript issue reports** (159 verified spans lost
   with no structural path, 54% of pre-packing loss; `entry_recall@20` 0.35). Not
   specific to TypeScript resolution; the retrieval R&D was closed for Python
   (lexical body search rejected), so a new hypothesis is needed before work starts.
2. **`tsconfig` `baseUrl`/`paths` and workspace-package resolution** (71 spans, 24%;
   89% of vscode imports are `baseUrl` aliases; 70% of mui's and 85% of vue's unresolved imports are workspace packages). It is
   the cheapest measured gain, and dev (vscode) can show it without reading held-out.
3. **Index scaling of LadybugDB loads**: the default buffer pool cannot index a
   4,000-file TypeScript repository. A product defect independent of quality.
4. **Router bounds** (64 spans, 22%; every real route stopped at a bound).
5. **JavaScript sources**: half of mui's annotated context is `.js`.
6. The object-literal method discrepancy (docs/typescript.md) needs a decision: keep
   the behavior and the corrected doc, or drop the symbols (a derivation change).

## Reproduction

```bash
uv run python tests/python/contextbench_ts.py fetch    # pinned corpora -> ~/.cache/oxide/contextbench-ts
uv run python tests/python/contextbench_ts.py run --out DIR
mise run contextbench-ts                               # fetch + the gate
```

`tasks.json` and `gold-audit.json` were generated once with
`uv run --with pyarrow python tests/python/contextbench_ts.py tasks|audit <full.parquet>`.
