# TOON as an agent-facing serialization: preregistration (2026-10-21)

Question: can [TOON](https://toonformat.dev/reference/spec) (spec 4.4, Python
`toon-format` 1.2.0) make OXIDE's search and context results cheaper for coding
agents to read **without** losing comprehension, correctness or interoperability?
This is a serialization experiment only. Retrieval, routing, selection, budgets,
provenance, storage and the MCP transport/contract are not changed. Every arm
serializes **the same structured value** (`dataclasses.asdict` of the API result,
normalized through JSON so tuples are lists).

This file, `scripts/`, the question templates and the criteria below are written
before any case is built, any size is computed, or any agent answer is scored.
Results go to `README.md` and do not edit this file. Before freezing it, its
sha256 is written to `$DATA/prereg.sha256` (DATA = `~/Projects/oxide-eval-data/oxide-toon-eval`).

## What was seen before the freeze (disclosed)

- **Code read:** `mcp_server.py`, `cli.py`, `models.py`, FastMCP 4.1.1's
  `default_serializer`. `mode=search` text is `pydantic` `dump_json` of the
  `SearchResult` (compact, raw UTF-8). It was measured to be **byte-identical** to
  `json.dumps(asdict(r), separators=(",", ":"), ensure_ascii=False)` on one fixture
  search. `mode=context` text is a one-line summary plus raw `payload`. The bundle's
  metadata is in `structured_content` only. CLI `--json` prints `json.dumps(indent=2)`.
- **One TOON rendering** of a 5-entry fixture `SearchResult`. Entries render in TOON
  **list form**, not tabular, because `seeds` is an array and `source` can be null.
  `sha256:` digests and keys containing `:` are quoted. `FileInfo.diagnostics` is an
  array, which also rules out the tabular form (spec §9.3). No size or token count was
  computed.
- **Upstream claims** ([benchmarks](https://toonformat.dev/guide/benchmarks), self-published,
  o200k_base): on mixed-structure data TOON is **+1.6 % vs compact JSON** and −32.7 %
  vs pretty JSON. On flat data it is −35.2 % vs compact JSON. On semi-uniform logs it is
  +19.9 % vs compact JSON. Accuracy differences mostly fall inside overlapping CIs.

## Arms

| arm | text shown to the model | today in OXIDE |
|---|---|---|
| **C** | compact JSON (`separators=(",",":")`, `ensure_ascii=False`) | MCP `mode=search` text (byte-identical) |
| **P** | pretty JSON, `indent=2`, `ensure_ascii=False` | CLI `--json` |
| **T** | `toon_format.encode(value)` with defaults (indent 2, comma delimiter) | no |
| T-tab | TOON with tab delimiter | tokens only, no agent calls |
| **HC / HT** | context bundles only: the envelope (the bundle with every `items[].text` removed) in C or T, then a blank line and the raw `payload` | no |
| M | context bundles only: today's MCP text (summary line + payload) | tokens only. It omits metadata, so it is not an information-equivalent arm |

Bundle agent arms are C, T, HC and HT. All other output kinds use C, T and P.

## Outputs (cases)

Real repositories: the 8 Python dev ContextBench tasks on real corpora (requests ×6,
seaborn, flask) and the 4 TypeScript dev tasks on code-server ×2 and darkreader ×2.
The query is the task's issue text, run on production retrieval with no hints. Per task:

- `search20` is `search(query, limit=20)` (MCP default) and `search100` is
  `search(query, limit=100)` (MCP max), for ranked search results.
- `files` is `files()` of the corpus, for file metadata (uniform records with an
  array field).
- `relations` is `relations(key)` for the symbol entity among the first 10 search
  entries with the most relations, for structural relationships (nullable nested
  `evidence`/`target`).
- `bundle` is `build_context(query, 2048)` (MCP default), for ContextBundle metadata
  plus source evidence.

Edge repository (`build.py edge`, synthetic, written into DATA): Unicode and space
paths (`src/données/模块.py`, `src/naïve café.py`, `web/ünï/コード.ts`), and source
with quotes, backslashes, `: `, leading `- ` and `#`, tabs, `"""`, template literals
and non-ASCII identifiers. Its cases are a hinted search with a `not_found` and a
resolved hint, an **empty** search (no lexical hit), `files`, `relations`, and a
bundle whose items contain those special lines.

Truncation: `search100` of the first requests task and the edge hinted search, each
cut textually just before the entry at position ⌈n/2⌉+1 begins, the way a client
output cap would cut them. Gold counts the complete entries that remain.

## Questions (deterministic gold from the structured value)

Each call shows one output in one arm and asks up to 5 questions. The model answers
with JSON `{"answers": {"q1": …}}`. Templates and their grading:

- **search:** the source path and start byte of the entry at position k (exact pair);
  keys of every entry with `test = true` (set); how many entries have a null
  signature (int); the name of the entry with `lexical_rank` r (exact); how many
  entries there are (int); edge only: the hints whose issue is `not_found` (set),
  and the keys of entries with at least one seed (set).
- **files:** the size of a named file (int); the digest of a named file (exact
  64-hex copy); how many files have a given language (int); how many files are
  `unsupported` (int); the paths of files with at least one diagnostic (set).
- **relations:** how many relations have kind k (int); the distinct sources of kind k2
  relations, where k2 has ≤ 10 (set); the names of unresolved relations (set); the
  evidence path and start of the relation at position i (exact pair); the target of
  the relation with site s and kind k (exact).
- **bundle:** used and budget (pair); omissions at stage `packing` (int); the path
  and lines of the item at position i (exact); keys of item entities with
  `complete = false` (set); `route.stopped_by` and `route.deferred` (pair);
  and **copy line n of file p exactly** (exact string, trailing whitespace ignored),
  with a line containing a quote, backslash, colon or tab preferred.
- **truncated:** how many entries are completely shown (int); is the output cut off
  (bool); the path and start of a visible entry (pair).
- **navigation (task success):** for each of the 12 real tasks, the `search20` output
  plus the issue: "choose at most 3 paths a developer should open first". Score:
  1 if any verified gold file is chosen, plus the fraction of gold files chosen.

Paths, keys and strings are compared exactly after trimming surrounding
whitespace. Sets compare as sets. An unparseable reply scores 0 on every question
of that call and counts as an error.

## Agent

OpenCode `opencode run --standalone --model openai/gpt-6-luna`, with the custom
no-tools agent and isolated config of `outline-comparison/scripts/nav.py`. The
working directory is empty, there is one turn, and the user prompt is fixed apart
from the output text and the questions. Two repetitions, calls shuffled with seed
20261021. Rate-limit retries are not evidence. Provider-reported input tokens are
recorded per call: they are the agent model's own tokenizer, measured. Offline
token counts use tiktoken `o200k_base` (primary) and `cl100k_base`, plus OXIDE
`oxide-units-v1`.

## Metrics

- **Size (deterministic):** bytes, o200k and cl100k tokens and units per output and
  arm. Savings are `1 − T/C` per output, reported as medians per kind, and pooled.
- **Runtime:** encode time (median and p95 of 50 runs per output) for T vs
  `json.dumps` C, `import toon_format` time, installed size and dependency count.
- **Conformance:** the official fixtures (`toon-format/spec` tests, pinned commit) run
  against `toon-format` 1.2.0, plus `decode(encode(v)) == v` for every OXIDE output,
  plus strict decode of every truncated text (does it detect the cut?).
- **Comprehension:** question accuracy per arm, pooled and per kind, with a paired
  bootstrap 95 % CI (10,000 resamples over cases) of T − C.
- **Task success:** navigation score per arm.
- **Errors and latency:** unparseable replies, failed calls, wall seconds per call.

## Acceptance criteria (T against C, today's MCP representation)

The MCP surface that could adopt TOON is the `mode=search` text, plus a possible
bundle envelope. Criteria S1 and A1–A3 are therefore computed on `search20`,
`search100`, the edge searches and the bundle envelope (HT vs HC). The other kinds
are reported, not gating.

- **S1 savings:** median o200k saving of T vs C ≥ 10 % on `search20`, and HT vs HC
  saves ≥ 10 % of the envelope tokens on bundles.
- **S2 provider tokens:** median per-call reduction in provider-reported input tokens
  (T vs C, same case and questions) ≥ 5 %.
- **A1 comprehension non-inferiority:** pooled accuracy T − C ≥ −0.02, with the
  bootstrap CI lower bound ≥ −0.05.
- **A2 no broken kind:** no output kind (including the non-gating ones) has T − C
  < −0.05.
- **A3 task success:** navigation T − C ≥ −0.05.
- **A4 truncation:** on truncated cases T is not worse than C by more than 0.10
  accuracy. A declared `[N]` that is no longer true must not make the model misreport
  the count.
- **R1 interoperability:** 100 % round-trip on OXIDE outputs. Official fixtures:
  every failure is listed, and any failure that affects OXIDE's value shapes fails R1.
- **R2 runtime:** p95 encode time for `search20` ≤ 5 ms, with no runtime dependency
  beyond the package itself.
- **V validity:** ≤ 5 % failed or unparseable calls in any arm.

**PASS:** all of S1, S2, A1–A4, R1, R2 and V hold. TOON is then proposed as an opt-in
`format` only, never a default.
**REJECT:** S1 fails (the shapes OXIDE emits do not shrink enough to matter), or A1's
point estimate is < −0.05, or A2, A3 or R1 fails.
**INCONCLUSIVE:** anything else, for example savings that hold while A1's CI spans
the margin, or V fails.

Any criterion that cannot be computed is reported as not computed. Its absence never
counts as a pass.
